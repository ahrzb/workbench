# Workbench skill: research synthesis

Research date: 2026-09-29. This file summarises the eleven research notes and the stack bake-off, and records the decisions and tensions that cut across them. The skill is called **workbench**. It helps someone who uses a computer all day but doesn't write code build small tools for a job, a hobby, a club, their household or a side project: they know their own subject, have no admin rights, sometimes use a managed (company) laptop, and use ChatGPT / Codex only. Each note has numbered recommendations, key evidence, open questions, conflicts with the guiding principles, and cited sources. In the notes, `[UNVERIFIED]` and `[INFERENCE]` mark claims not confirmed against a primary source, and `[LOCAL]` marks something tested on one Windows 11 machine (build 26200, standard user). Tags in this file follow the notes.

Current decisions in one line: Electron + TypeScript; every tool downloads into the project's `.tools/`; several tools per project, each in `tools/<name>/`; `node:sqlite` + ExcelJS for data, with tested building blocks for backups, Excel and AI reading; AI features in a built tool call `codex exec` under the user's ChatGPT plan; the assistant-driven (MCP) path is Codex-only; HTML sketches at real forks; save points; a startup hook plus `AGENTS.md`; security and compliance rules that always hold; websites only on the user's own Cloudflare account, private by default; `CONTEXT.md` per tool and small-turn questioning.

## Headline recommendations per area

**1. Interview** ([01](01-interview.md))
- Run a fixed, time-boxed interview of about 15–25 minutes in six stages: frame → one real past episode → walk the current workaround → stakes → slice → confirm. Each stage has exit criteria. Structured elicitation beat free-form LLM chat in the three LLM-interviewer studies found (LLMREI, ReqElicitGym, OntoAgent). All three used simulated or role-played users.
- Open with "Tell me about the last time you…" (Torres; Fitzpatrick's *Mom Test*), never "what features do you want?". When the user names a feature, ask *when* they needed it (Shape Up's calendar case). If they can't recall an episode, do one live.
- One question per turn. Start with a neutral echo, not praise. Close by asking "What did I get wrong?". LLMs that jump to solutions early "get lost and do not recover" (Laban et al., 39% multi-turn drop), so don't build before the exit criteria are met.
- Steer small: "the one moment last week you'd most like to skip", a fixed appetite ("useful by tomorrow morning"), a visible Later list, and the user's real episode as the acceptance test.

**2. Vocabulary** ([02](02-ontology-vocabulary.md))
- Take the vocabulary from the user's story, not from a definitions exercise (Domain Storytelling, EventStorming). Their words are canonical: people choose the same word for a thing less than 20% of the time (Furnas 1987). Sort terms into Things / Actions / Rules only; keep the mapping to software concepts out of the user's sight.
- Introduce a technical term only if it is needed now, will recur, and has no plain description of about eight words. Pattern: bridge from their word → name plus one-line meaning → why now → an example from their data → teach-back (AHRQ; never "does that make sense?") → log it.
- Sizes are heuristics from working-memory and second-language studies, not measured for glossaries: 8–15 of the user's words at the start, 0 borrowed software words at the start and at most ~5 active, at most 1 new term per message and 3 per session, about 15–25 lines in all.
- Keep "careful words" (false friends such as file, report, form, backup) and a Retired list. The glossary template in this note is superseded by `CONTEXT.md` ([09](09-context-file.md)); the reasoning behind each section still stands.

**3a. Runtime, UI, install** ([03a](03a-default-stack-runtime.md), [bakeoff/](bakeoff/))
- **Default: Electron + TypeScript** (Forge + Vite, Node 24 LTS, npm only), always started from the skill's hardened starter (`starters/electron/`), never a fresh scaffold. **Fallback: one self-contained HTML file** opened from disk, which no application-control policy can stop. Note 03a proposed reusing the Electron UI through a shim over `window.api`; the shipped `starters/html/` is its own starter instead: hash-based CSP, `build.mjs`, Export/Restore backup, 12 tests, and zero CSP violations and zero network requests in headless Edge [LOCAL]. Bake-off: Electron was the only option that was admin-free, network-clean *and* HTML-rendering; the Python + system-webview build phoned Microsoft (2–3 HTTPS connections from WebView2, not stoppable); Tauri, Flutter and React Native needed a C++ toolchain (admin); Compose and Avalonia can't render HTML. Code quality was a tie across the four that finished.
- **Nothing is installed.** Node comes from the official zip or tarball (hash-checked) into `.tools/node`; npm's and Electron's caches live in `.tools/` too; a launcher sets PATH per process; on Windows always `npm.cmd`. Files fetched from the terminal carry no Mark-of-the-Web, so SmartScreen and Gatekeeper stay quiet. The whole in-project run took 72 s and about 1.45 GB [LOCAL]; several tools in one project share `.tools`, so the first Electron tool is about 1.5 GB and each further one about 0.4 GB. The app is built on the user's machine and run from the tool's own `current/` folder; besides each tool's data in AppData, one desktop shortcut per tool is the only change outside the project.
- **No native Node modules** (they need a compiler, which needs admin). The starter is hardened and the agent never loosens it: sandboxed renderer, context isolation, own `app://` protocol with a strict CSP, no navigation or permissions, only the native Open/Save dialogs touch files, Electron fuses. **Offline is proven, not assumed**: a stock Electron app downloaded a spellcheck dictionary on first launch, so every build ends with a check of the app's network connections (expected: 0).
- Corporate networks: `NODE_USE_SYSTEM_CA=1` for TLS inspection, proxy variables (set both schemes), a short list of hosts, and a blocked-environment ladder that ends with a message for IT. Never bypass a control.
- **Smart App Control** (SAC) is the main open risk: 5 of 7 PE files in the official Electron zip are unsigned. This was not tested on a machine with SAC enforcing; a block goes to the HTML-only tier. macOS is untested; its plan is from docs only.

**3b. Data** ([03b](03b-data-storage.md))
- Ask one question first: "Who is the source of truth, and will a person open, edit or email this file?" If the app owns the records, use SQLite; if the user owns them in Excel, they stay there. v1 usually needs no database: read the user's file, write a new output file. Once the app has data of its own: read Excel → own SQLite → export xlsx.
- Never write into the user's original spreadsheet. ExcelJS and SheetJS CE silently dropped charts, shapes and extension validations on a load-and-save with no warning [LOCAL], so treat any library warning as a stop sign. Preflight the file (Excel lock, synced folder, real xlsx), match columns by header name, store IDs as text, read cached values, write dates in UTC. In-place edits are a last-resort ladder that starts with "don't".
- SQLite is Node's built-in `node:sqlite` in the main process only (no package, no native module; stability "release candidate"). One connection with a busy timeout, `STRICT` tables, the default rollback journal, one transaction per user action, backups through `backup()` (the shipped block uses `VACUUM INTO`), and numbered migrations with `PRAGMA user_version` and a backup first (the shipped block keeps the version in `data\version.json`, so it also covers files that are not SQLite). New xlsx files: ExcelJS 4.4.0, written to a temp name and renamed to a new unique name. Shipped as tested blocks (v0.2.0): `blocks/data-safety/` (backups, migrations run on a private copy, refusal of newer data, restore that keeps a `before-restore` copy, a command line for the AI; 20 tests; packaged app verified) and `blocks/excel/` (read by header, IDs as text, typed dates and numbers, csv dialects, ExcelJS pinned; 31 tests). The data-safety block also found a real starter bug: Vite stubbed out `node:sqlite` until the starter's `vite.main.config.mts` externalised it.
- App data goes in `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\data` as shipped (03b recommends `%LOCALAPPDATA%\<App>\data\`; macOS `~/Library/Application Support/<App>/data/`, untested). `TOOL_ID` is a short name plus 6 random letters, fixed when the starter is copied and independent of the display name. Not the project folder, not Documents or Desktop, never a network or synced drive; setup refuses synced or network project folders. Backups of real data go to `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\backups\<yyyy-mm-dd-hhmm>[-label]\`, beside `data` and outside the project (v0.1.x used `%LOCALAPPDATA%\Workbench\backups\<project folder>\`). Electron's default folder is the Roaming one, which some environments back up to the cloud. Note 03b also proposes "Export everything to Excel", "Back up now" and "Open data folder" buttons; the starter has none, but the data-safety block ships an optional Backups screen (list, back up now, go back to a copy).

**4. AI in the tool, and the assistant doing the legwork** ([04a](04a-software-2-llm-extraction.md), [04b](04b-software-3-local-mcp.md))
- Classify in order and stop at the first yes. (1) Can the user state the rule completely? → code. (2) Is the input messy but the output shape fixed and the steps known? → one AI call per document, with a schema and a code validator. (3) Judgment across sources with an unknown number of steps? → the user's own assistant through a local MCP server. (3-lite) Low volume, or no Codex, or IT blocks MCP? → export a review view and the user pastes it into their assistant. Don't ask "rules or AI?": run the user's own sample both ways and show accuracy, time, plan usage, where the data goes, and offline or not.
- Rules before models, per document: embedded e-invoice XML, then the PDF text layer, then regex, then a model. Send page images rather than OCR text (image input won by 11–40 points in the Fraunhofer benchmark); render PDF pages with pdf.js first, because a PDF passed to `codex exec -i` came back empty.
- **No key, no separate bill.** The tool runs `codex exec` under the user's ChatGPT sign-in, locked down: `--ignore-user-config --ephemeral --skip-git-repo-check -s read-only` (shipped without `--ignore-rules`, so user and company rules stay in force), an empty folder, a fixed list of `--disable`d tools (shipped with `code_mode_host` added), `--output-schema`. The packaged tool ships `codex.exe` (Forge `extraResource`) and calls it from `process.resourcesPath`; tested from the packaged folder with PATH reduced to System32: 4.6 s, correct fields [LOCAL]. Tested on a made-up invoice with the earlier flag set: 7.3 s, ~8.6k tokens in and ~270 out, every field right, a hidden instruction flagged, no commands run [LOCAL]. The SDK with defaults loaded the user's own MCP servers and ran shell commands on a PDF, so don't use it. The account type (read from the sign-in) decides the data question, and the cost is stated per account type (personal: part of the plan's allowance; company: a question to IT); there is no separate consent screen. Since v0.2.0 the call ships as the tested `blocks/ai-read/` block (37 tests): real calls from the packaged app on a made-up injection invoice read every field right, flagged the injection, took 7–9 s and used about 12.4k tokens in and 178 out [LOCAL]; `codex.exe` adds about 310 MB to the packaged app.
- Ship a validator with every extractor and reject empty or zero results *before* the sum checks (0 + 0 = 0 passed). Keep the model name in one setting: Codex models are retired on a schedule and a retired name fails with exit code 1, so the tool must fall back to rules and say so. Model output is shape, not truth.
- MCP is Codex-only: ChatGPT web only reaches remote servers, and the skill never builds a hosted server, tunnel or account. Stdio only, registered in the project's `.codex/config.toml` (works only once the user trusts the folder), pinned SDK, tools only, read-only by default, no outbound network, narrow tools (no arbitrary SQL, shell or paths), writes as proposals that a person commits in the app, every returned string treated as attacker-controlled. IT may block MCP; keep a non-MCP route.

**5. Sketches** ([05](05-mockups-alternatives.md))
- Show alternatives only at real structural forks. Show 2–3 options, never 1 and never more than 3. Tohidi et al. 2006: users shown a single design rated it higher and never rejected it. Dow et al. 2010: parallel prototyping gave better results, most of all for novices. Skip it for trivial forks: sketches must not become a second build trap.
- Options differ in how the user would *use* the tool (layout, flow, interaction model, density, automated vs manual), one named dimension at a time. Visual style is frozen. Name each option in the user's words. AI-made options converge unless the dimension is forced.
- Default format: one static, greyscale, self-contained HTML sketch with the user's (sample) data and a "SKETCH — not the real app" banner, and a Content-Security-Policy `<meta>` tag so it loads nothing external (0 of 6 requests with the tag vs 6 of 6 without [LOCAL]), saved in the tool's own `sketches/` folder. It is honest because the real UI is HTML too. The case for *low fidelity* is weaker than folklore suggests; the strong evidence is for *multiple alternatives*.
- Present side by side with one-line tradeoffs. Ask the user to run one real task through each. Allow mixing and "none of these". Give the recommendation last. For "AI or code?", show the two results side by side instead of two screens.

**6. Build loop** ([06](06-build-loop.md))
- Seven steps per change: orient → echo the change in the user's words → size it to one try-step → save point → build and verify → hand back ("Done / Try it now / You should see / What I checked / Next I could…") → read the reaction. The first build is a small end-to-end slice, never called an "MVP". Never claim "works" without saying what was run.
- Milestones and demos (v0.2.2, after the user saw the AI build a whole version before checking its design): a plan of 3-5 milestones shown and agreed before building, cheapest and riskiest first: first look (the result on the user's samples, before any app), the shape (how they'll use it, a rough sketch), the hard part proven, the thinnest working tool, then widening. Every milestone ends in a demo; one milestone per turn, then wait; check in at once on a surprise, a choice that changes what they'll see, a growing milestone or two failed attempts. The starter is copied only at the thinnest-working-tool milestone.
- The user tries it (v0.2.6, after the owner's real project never showed them a demo): in their Codex sessions the AI checked the tool itself in hidden windows, then replaced the copy behind their desktop shortcut without their try, and the fix route had no trying-out step at all. Now a demo is the user trying it: a clickable greyscale sketch at "the shape" (tested [LOCAL]: Codex made one on sample rows; marking a member paid updated the list), and after every milestone and every fix the trying-out copy opens in front of them with two or three things to do and "Does it work the way you want, and do you like how it looks and feels?" Their copy changes only after their yes (tested through Codex on a fix: trying-out window opened, desktop copy untouched until "yes", then shipped and `In use:` updated).
- Showing pages, and helpers in Bun (v0.2.7). In the owner's own session the AI opened the sketch with an escalated `Start-Process`, said "I've opened a clickable layout sketch" with no link, and the user had to ask "which layout?"; clicking the link it then gave opened the page in the Codex app's browser panel. So a page (sketch, data map) is shown as a link at the top of the reply, again with "Updated: ..." after every change, and never claimed as opened (tested through Codex [LOCAL]: link first on the first sketch and on its update). Once a tool has screens, sketches of changes reuse its stylesheet and class names (tested: the recipe-box sketch carried its colour tokens, serif type, masthead, cards and buttons). The workbench's own helpers (`save`, `try`, `data-map`, `update`) are now Bun TypeScript, one file for Windows and macOS, run through `run.cmd` with Bun 1.4.2 pinned by SHA-256 in `bootstrap.ps1` (the Windows `bun.exe` carries a valid Authenticode signature [LOCAL]); only what must run before anything is downloaded stays PowerShell/sh (bootstrap, the startup hook, the account check, the launchers). The AI's own throwaway scripts are Bun too, in `.workbench/scratch/`. Tested [LOCAL]: inside Codex's sandbox (approval policy "never"), `save.ts` and `data-map.ts` ran and a Bun scratch script totalled 240 payment rows correctly and was deleted; outside it, `try.ts` and `update.ts` matched the old scripts' output (real 0.2.5 -> 0.2.6 update, forced failure restoring 175 files byte-identical), and `bootstrap.ps1` replaced a running `bun.exe` by renaming it. Known gap: a 0.2.6 project updating to 0.2.7 runs its old `update.ps1`, whose final save point calls the now-removed `save.ps1` and is skipped; the next save point covers it.
- Save points before and after every change, invisible to the user, with their words as the message (prefixed with the tool's name). Codex's default sandbox keeps `.git`, `.agents` and `.codex` read-only (a `git add` failed with a permission error [LOCAL]), so the history lives in `.workbench/`. Each save point is built by `save.ts` (before 0.2.7: `save.ps1` / `save.sh`) from an explicit list of permitted files covering every tool, so no ignore rule can let documents or secrets in. "Go back" is for one tool only (`git.cmd restore --source=<save point> --staged --worktree -- tools/<name>`), so other tools are untouched [LOCAL]; it rebuilds and redeploys that tool and first tests the older version against a copy of the current data (the data-safety block's `copy` command; a refusal shows up in `start-problem.txt`). Data gets its own dated backups in `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\backups\`, outside the project and outside the save points (the 2025 Replit incident). The engine choice is disputed: see "Recorded disagreements" below.
- After two failed fixes, go back to the save point and restart in a clean context. Keep an "ideas shelf" and never build extras the user didn't ask for. Every ~5 changes, tidy up without changing behaviour. Each tool carries its own project memory: `tools/<name>/CONTEXT.md` (words) and `tools/<name>/NOTES.md` (everything else); `.workbench/NOTES.md` is only the project list.
- Say plainly when the project is growing (others rely on it, it holds other people's data, it needs logins or payments, mistakes would be costly), then help the user carry the extra responsibility rather than stopping ([08](08-security-compliance.md) rec 8). Problems outside the tool become a forwardable question, not a debugging session.

**7. Host: Codex** ([07](07-codex-host.md))
- Two layers: a project `SessionStart` hook that injects the session brief, `.workbench/NOTES.md` (the project list), the `CONTEXT.md` and `NOTES.md` of the tool named in `Last worked on:` and the last 5 save points, and `AGENTS.md` as the backstop. The shipped hook withholds all of those notes unless the current ChatGPT sign-in matches the account recorded for the project (rec 8 below). Tested [LOCAL]: hook trusted → welcome in 7 s, ~17k tokens; hook skipped (untrusted folder) → `AGENTS.md` still gets the welcome, in 28 s, ~51k tokens. With several tools [LOCAL, Codex CLI 0.157.1]: a two-tool welcome, a fix routed to the other tool, a new tool created and registered, per-tool go back leaving the other tools untouched, the account gate withholding all notes, and a hostile `Last worked on: ../secrets` line ignored. The hook fires on the user's first message and matches `startup|clear` only. Plain stdout, not JSON. On Windows it is a PowerShell 5.1 script with no Node.
- The `workbench-setup` skill is copied into the empty project folder by one pasted line (download the release, copy `skills/workbench-setup` to `.agents/skills/workbench-setup`, follow its `SKILL.md`); it copies the project template and deletes itself in one command, so nothing is installed per computer. Setup costs the user three clicks: approve writing `.codex/` and `.agents/`, trust the folder, review the startup check (Review hooks → Allow selected). The agent never approves for them. Skills can't ship hooks, and a plugin's hook would run in every Codex session, so the hook lives in the project.
- The skill needs the Codex surface (app, CLI or IDE): ChatGPT web has no folder access and no local hooks. The CLI installs per user; the Windows app comes from the Microsoft Store and may need an admin to approve it on a managed laptop [UNVERIFIED for personal PCs].
- Update: the user says "update the workbench". The AI reads `.workbench/VERSION`, finds the latest *tagged* GitHub release of the repository named there, resolves it to its commit and downloads that exact commit with `curl.exe` + `tar`, then tells the user in plain words what changes: the `CHANGES.md` lines and, separately, anything that changes what runs by itself, what is downloaded or what the AI may read, change or send. After a yes it copies every skill-owned path into `.workbench/update/before/` (used for recovery, not the new helpers) and makes a save point, then replaces only skill-owned files (`.agents/skills/workbench/`, `.workbench/scripts/`, the session brief, `.codex/hooks/` and `hooks.json`, `AGENTS.md`, `.gitignore`, `.gitattributes`), keeps `hooks.json` stable (Codex re-asks for review on any change), writes `.workbench/VERSION` last, and asks for a new chat. Never `tools/` (every tool's notes, words, code, samples and copy in use), `.workbench/NOTES.md`, `.workbench/account`, the tools' data and backups or `.tools/`; an update from 0.1.x first moves the one existing tool into `tools/<name>/`. Nothing checks for updates on its own. Open decision for the maintainer: authenticated (signed) releases for updates.

**8. Security and compliance** ([08](08-security-compliance.md))
- Rules that hold in every chat, in the session brief: no listening services, no accounts or cloud of the tool's own (the one exception is a website on the user's own Cloudflare account, private until they choose public; its local preview uses `127.0.0.1` only while checking), no admin and no workaround around a security control, originals read-only with a backup first, nothing sent without the user knowing where it goes, no secrets, the Electron hardening as the baseline.
- Ask whose data it is and whether rules apply; don't assume, and the user's answer decides. When real files first come up, unless "About the user" in `.workbench/NOTES.md` already answers it, the AI asks once, in one line with its guess: "Is this for your own <guess>, or for work? If it's for work, are there rules I should keep in mind, like data protection or company policy?" Their own, or work with no rules to mind: use them, nothing to say. Work with rules (or unsure): follow them; on a personal plan, one line on where files go, then the user's call; look-alikes and a forwardable IT question only if they're unsure. (v0.1.0 assumed work data and pushed made-up samples by default; up to v0.2.0 the persona itself read "office worker, their own work, often a company laptop", which the user found paranoid: a resume parser read as hiring data. v0.2.1 records the wider persona and how they use the workbench, see section 9.) `.workbench/scripts/account.ps1` / `.sh` read Codex's sign-in file (plan type and account id; not a documented interface) and print `personal <id>`, `company <id>` (first 12 hex digits of the SHA-256 of the account id) or `unknown`. `.workbench/account` records it silently at setup, or `unverified` for keyring sign-ins that can't be read, and the startup hook withholds `.workbench/NOTES.md` and the tool's `CONTEXT.md` and `NOTES.md` unless the current sign-in matches exactly [LOCAL: tested with synthetic auth files; a two-tool project withheld all notes].
- The user never gets a technical question. The worst case is one self-contained, forwardable message with a default ("If that's not possible, I'll…"), logged under "Waiting on". The user can ask for one about anything, any time, for IT (policy facts) or a tech-savvy friend (technical detail).
- Sharing is supported, never refused: name the new responsibilities one at a time. Sharing ladder: one HTML file or a private website → each person builds their own copy (`tools/<name>/app` only) → unsigned zip → IT signs and deploys → self-signing (which makes the user a publisher; costs stated first). Unsigned apps show "Windows protected your PC", and SAC blocks them outright.
- Websites are allowed (the user's decision, v0.2.0): `starters/web/` on the user's own Cloudflare account, private behind Cloudflare Access by default, public only after the AI asks and the user understands; see section 10 and [08](08-security-compliance.md) rec 9.

**9. CONTEXT.md and questioning** ([09](09-context-file.md))
- The persona is tech-savvy but not a developer, builds tools for their job and just as often for themselves, and judges their own risks. They want the AI to get on with it: no warnings, checks or questions they didn't ask for unless one saves them from something they'd regret. What the AI learns about them goes in a few lines under "About the user" in `.workbench/NOTES.md`, picked up in conversation, never by interview.
- One `CONTEXT.md` per tool (`tools/<name>/CONTEXT.md`; two tools may use a word differently): a glossary in the user's words and nothing else (no decisions, progress or spec), 15–25 entries, sections created when they get their first entry. Names are settled in a short dialogue: the user's word wins; if they have none, the AI offers one in a sentence from their own case. Written the moment a word settles, with one line of announcement. A rename changes everything in one sweep, and the old word goes to Retired.
- Check or ask, whichever is quicker for the user: the machine, files and formats are the AI's to check; facts about their own case are often quicker to ask, and the AI offers to check instead. Technical choices are never questions. Ask only when a wrong guess is expensive; otherwise pick a default and say it in one line.
- Small turns: one question per message, only about things the user can answer from their own experience today, always with a suggested answer. "I don't know" is the AI's mistake. Pre-send check on every message against the glossary.
- Cover two blind spots: the usual case vs the case that ruins it (sort exceptions by "what if we get this one wrong?"), and knowledge that lives only in the user's head. Sort what the user says into goal, need, requirement, guideline, want and solution; challenge a solution stated as a need and a rule the data contradicts.

**10. Several tools, starters and blocks** (built after the notes in v0.2.0; there is no separate note)
- **Several tools in one project.** Each tool lives in `tools/<name>/` (lowercase letters, digits, hyphens) with its own `NOTES.md`, `CONTEXT.md`, `app/`, `samples/`, `current/` (the copy the desktop shortcut points to) and `sketches/`. Shared: setup, `.tools/`, the startup check and the save-point history. `.workbench/NOTES.md` is now the project list: `Last worked on: <name>`, "Tools here", project-level "Waiting on" and the ChatGPT account. The startup hook injects the brief, that list and the last-worked-on tool's CONTEXT and NOTES, behind the same account gate. Save points cover all tools, with messages prefixed `<tool>: `; "go back" restores one tool. Tested [LOCAL, Codex CLI 0.157.1]: a two-tool welcome, a fix routed to the other tool, a new tool created and registered, per-tool go back leaving the others untouched, the account gate withholding all notes, and a hostile `Last worked on: ../secrets` ignored. Not tested: more than two tools, macOS.

## Cross-cutting findings

These come from reading the notes side by side. Most are not visible from a single note.

### Recorded disagreements

**A. Which engine makes save points.**
- [06](06-build-loop.md) recommends **isomorphic-git** as the default on both systems: a skill-owned `save-points.mjs` run by the project's Node, history in `.workbench/history.git`, and a journal file `.workbench/save-points.txt` that the startup hook reads instead of calling git. Reasons: MinGit's executables are unsigned (not tested under AppLocker, WDAC or SAC), macOS has no admin-free git, `node.exe` is signed and already needed, and it was the only path tested end to end. MinGit is its Windows fallback 1, `tar` snapshots fallback 2. Its script keeps files out with an ignore list in `.gitignore`.
- [03a](03a-default-stack-runtime.md) rec 24 and the **shipped template (v0.1.0, unchanged in v0.2.0)** use real git: `.workbench/scripts/git.cmd` runs the system `git`, or the MinGit that `bootstrap.ps1` downloads into `.tools\git` only when git is missing, with `--git-dir=.workbench\history`. Each save point is made by `.workbench/scripts/save.ps1` / `save.sh` from an **explicit list of permitted files**: the index is rebuilt with `read-tree --empty` and `add -f --pathspec-from-file`. The shipped `.gitignore` is still an allowlist but only as a second layer, because a nested `.gitignore` inside the project could override an ignore-based allowlist and let documents or secrets into a save point. The hook runs `git log`. On macOS, `save.sh` uses git only when it is safe (`xcode-select -p` succeeds, or a project-local git exists) and otherwise makes folder snapshots in `.workbench/snapshots/`. 03a lists isomorphic-git only as tier 4 (no git binary).
- Both agree on the part that was tested: history must live outside `.git`, because Codex's sandbox keeps `.git` read-only. Both write standard git repositories (06 checked that MinGit and isomorphic-git read each other's), so switching later loses nothing, but the folder names differ.
- What the shipped choice gains: real git commands the model already knows, no bundled library, no home-made workaround for isomorphic-git's same-second stat bug, and an explicit file list that doesn't depend on ignore rules. What it loses: an unsigned `git.exe` on a laptop that has no git (untested under application control) and no engine at all on a Mac without the Command Line Tools.
- **Not resolved.** A small step that would close the Mac and blocked-`git.exe` gaps, and that this file suggests rather than the notes prove [INFERENCE]: ship 06's script as the fallback *ahead of* snapshots, pointed at the same `.workbench/history` folder and rewritten to use the same explicit file list instead of 06's ignore list. The choice of default belongs to the skill author.

**B. Where the app's data lives, and what an update touches.**
- [03b](03b-data-storage.md) rec 3 puts app-owned data in `%LOCALAPPDATA%\<App>\data\`, outside the project. [07](07-codex-host.md) rec 11 says an update never touches "its data" without saying where that is.
- **Consistent reading:** the tool's own data (the SQLite file) lives in `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\data`, and the backups beside it in `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\backups\` (v0.1.x: `%LOCALAPPDATA%\Workbench\backups\<project folder>\`), both outside the project. So code can go back to an old save point without dragging the database with it, the update only replaces skill-owned files, and the data is out of its reach by location and not only by an exclusion list. "Its data" in 07 means those folders. What stays *inside* the project and is also never touched by an update: `tools/` (each tool's `NOTES.md`, `CONTEXT.md`, `app/`, `samples/` and `current/`), `.workbench/NOTES.md`, `.workbench/account`, `.workbench/history/` and `.workbench/snapshots/`, and `.tools/`. Dated copies of the user's originals are *not* in the project (an earlier draft had `.workbench/backups/`). `update.md` and `safety.md` ("replace the folder, data stays") fit this reading.
- Two knock-ons. (1) The original claim in [03a](03a-default-stack-runtime.md) rec 12 that deleting the project folder and the shortcut removes everything stopped being true once a tool has data; 03a now says so, and the shipped `stack.md` lists the tool's folder `tools/<name>/`, its shortcut and `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>` (data and backups) as things to delete, and asks before deleting any data. (2) 06's ignore-list entry `data/` assumes data inside the project; it isn't needed, because the shipped save scripts add only an explicit list of files and the shipped `.gitignore` doesn't carry it.

### Findings that still hold, updated

1. **The AI doing the building is itself a cloud data flow.** Anything the user pastes, shows or lets the agent open goes to OpenAI under their ChatGPT account: interview artifacts, sample data in sketches, files read while debugging, the startup hook's notes and save-point titles, and MCP tool results ([01](01-interview.md), [07](07-codex-host.md), [04a](04a-software-2-llm-extraction.md), [04b](04b-software-3-local-mcp.md)). The promise that can be kept is therefore "nothing is sent *without you knowing where it goes*", met by one plain sentence at the start, the account-type check and made-up samples when needed, not by architecture. Two places still promise more: [01](01-interview.md) stage 0 ("nothing leaves the computer without their okay") and the sample brief in [07](07-codex-host.md) ("unless… agreed"). The shipped brief and `build.md` already use the softer, true wording. NOTES must hold descriptions of the data, never the data.
2. **The "1.0 / 2.0 / 3.0" labels are a reinterpretation of Karpathy.** In his usage 2.0 means learned neural-network weights and 3.0 means prompting an LLM in English, so "call a model" is his 3.0 ([04a](04a-software-2-llm-extraction.md) R1). 04a and 04b use 2.0 = one AI call, 3.0 = the assistant doing the legwork. The shipped skill avoids the numbers ("plain rules / one AI call / no new tool"). Keep them internal and don't cite Karpathy for them.
3. **OneDrive Known Folder Move and iCloud Desktop & Documents break local-first silently.** The app-data folder covers the database ([03b](03b-data-storage.md)); the shipped starter has no startup guard on the data path. Setup refuses Desktop, Documents, Downloads, the home folder and drive roots, and a project path under `$env:OneDrive` or `$env:OneDriveCommercial`, a folder named like `OneDrive`, `Dropbox`, `Google Drive`, `iCloud` or `Box`, or a network path starting with `\\`, and suggests `%USERPROFILE%\Workbench\<name>`. The check works by path and name, so a synced folder that matches none of them would still pass [INFERENCE]; it would upload about 1.5 GB of rebuildable files (`.tools`, `node_modules`, `out`) and the churning `.workbench/history` objects. Say where the project folder syncs; never put a database or backups there.
4. **Growing projects.** Sharing is supported; the responsibilities are named one at a time ([08](08-security-compliance.md) rec 8, [06](06-build-loop.md) rec 20). New: a workbench folder *received* from someone else runs its startup hook and MCP server (`.tools/node/node.exe`) as soon as it is trusted ([04b](04b-software-3-local-mcp.md) rec 7). The shipped sharing ladder's rung 2 ("each person builds their own copy") avoids most of this: it shares only `tools/<name>/app` (through `git.cmd archive … -- tools/<name>/app`), so `.codex/` doesn't travel, and the recipient's AI compares `package.json` and the lockfile with the starter's before installing. A whole workbench folder received some other way still needs someone to look at `.codex/` before it is trusted; `safety.md` doesn't say so.
5. **The admin-free rule has holes.** Each has a detection step and a fallback in the notes; none was tested on a machine where it bites.
   - **Smart App Control (Windows 11).** It blocks unsigned code with no per-app bypass and turns itself off on enterprise-managed PCs, so it mostly hits personal PCs. Unsigned executables in the standard path are now: `electron.exe` and four DLLs ([03a](03a-default-stack-runtime.md) rec 22), MinGit's `git.exe`/`sh.exe` ([06](06-build-loop.md)), and possibly the `codex.exe` that a built tool with an AI feature now packages ([04a](04a-software-2-llm-extraction.md), signing and SAC untested). `node.exe` is signed. A block sends the user to the HTML-only version, which has no AI feature and no undo unless save points fall back to snapshots.
   - **macOS.** The system `git` is a stub that opens the Xcode Command Line Tools installer, which asks for admin. Every hook and script must check `xcode-select -p` first. Whether `codesign` works without those tools is the biggest unknown ([03a](03a-default-stack-runtime.md) rec 23). Nothing was run on a Mac.
   - **Group Policy and Constrained Language Mode.** A Group Policy execution policy beats `-ExecutionPolicy Bypass`, so the startup hook can be skipped silently (the `AGENTS.md` backstop covers it) and so can the shipped `bootstrap.ps1`. [03a](03a-default-stack-runtime.md) says its standard path needs no `.ps1` (`curl.exe` + `tar`); the shipped skill keeps that only as the manual macOS recipe. Under CLM the desktop-shortcut step (`WScript.Shell`) may fail: tell the user where the `.exe` is. The Store build of `pwsh.exe` makes all command hooks fail (openai/codex#47810).
   - **Codex itself.** The rule covers what the skill adds, not the host. The Codex CLI installs per user, but the Windows app comes from the Microsoft Store and may need an admin to approve it on a managed laptop, and Codex's "elevated" Windows sandbox needs one admin-approved setup ([07](07-codex-host.md) rec 9).
6. **Mockups compete with the build-trap principle.** Skip them for trivial forks, one screen per option, time-boxed ([05](05-mockups-alternatives.md) Conflicts). Because the UI is HTML, sketches and app share material, which is what makes them honest.
7. **"Ontology first" means "before building", not "before interviewing".** The vocabulary comes out of the interview's story steps. A few safety words ("stays on this computer", "backup", "sent to an AI service") must be taught early even though the rule is to avoid software terms ([01](01-interview.md), [02](02-ontology-vocabulary.md)).
8. **Project files are consolidated.** Each tool has its own `tools/<name>/CONTEXT.md` (the user's words, including careful and retired words). `tools/<name>/NOTES.md` holds everything else about that tool: what it is, interview status, next step, what we're after, how to run and check, things that work, the ideas shelf, waiting on, decisions, data, careful, notes for the AI; `.workbench/NOTES.md` is only the project list. The earlier separate glossary file, a decision log and the environment record are gone; the preflight result is no longer stored. One name for the Later list (ideas shelf) is used everywhere; mixing "backlog" and "parking lot" is the synonym drift [02](02-ontology-vocabulary.md) warns about.

### New, from reading the notes together

9. **Updates hit the same approval prompt as setup.** Codex's default sandbox protects `.agents/` and `.codex/` ([07](07-codex-host.md) rec 7, [06](06-build-loop.md) [40]). "Update the workbench" replaces `.agents/skills/workbench/` and `.codex/hooks/`, so it needs the same click, and the AI can't quietly edit its own skill. [07](07-codex-host.md) rec 11 and `update.md` don't warn the user.
10. **Updates can change what the hook runs without a new review.** Codex trusts a hook by the hash of its definition in `hooks.json`, not of the script it runs ([07](07-codex-host.md)). That makes quiet updates possible, and it is why updates come only from the repository named in `VERSION`, as an exact commit (a tag can move), with every change to what runs or what the AI may do listed in plain words first, and why nothing contacts GitHub unasked. Nothing authenticates the release itself: whoever controls that repository controls the update. Open decision for the maintainer: authenticated (signed) releases for updates.
11. **The Windows sandbox mode for a no-admin user is unsettled, and three notes depend on it.** With `--ignore-user-config` and no `windows.sandbox` setting, commands under `workspace-write` were rejected until `unelevated` was set ([06](06-build-loop.md)); [04a](04a-software-2-llm-extraction.md) doesn't know whether `-s read-only` needs anything elevated on a locked-down laptop; [07](07-codex-host.md) says the elevated mode needs one admin-approved setup and Codex falls back to unelevated without it. The in-tool AI call and save points both ride on this.
12. **The disk budget grows with each feature.** About 1.5 GB for the first Electron tool in a project ([03a](03a-default-stack-runtime.md) measured 1.45 GB), then about 0.4 GB for each further tool, because `.tools` (Node) and the npm and Electron caches are shared. A tool that uses `ai-read` adds about 0.31 GB to its packaged app for `codex.exe` [LOCAL]; the `@openai/codex` install itself was measured earlier at about 0.45 GB ([04a](04a-software-2-llm-extraction.md)); MinGit adds about 0.1 GB when git is missing [INFERENCE from the notes' figures]. The preflight rule of at least 3 GB free is in 03a but not in the shipped skill; `stack.md` says "about 1.5 GB for the first Electron tool … then about 0.4 GB more per tool".
13. **An MCP reader and the app would share one SQLite file.** [03b](03b-data-storage.md) designs for one writer with the default rollback journal, and a second connection couldn't write while the first held a lock [LOCAL]. [04b](04b-software-3-local-mcp.md) opens the same database read-only from a second process. Both need a busy timeout; concurrent use was not tested [INFERENCE]. On Windows, Codex passes `LOCALAPPDATA` to the server, so it can find the folder outside the project; macOS is unknown.
14. **Each note is only as current as its last edit.** [06](06-build-loop.md) names the history folder `history.git`, and several notes still describe the one-tool layout (a root `CONTEXT.md`, `app/`, `tool/<App>/`) that v0.2.0 replaced with `tools/<name>/`. Read the shipped skill as the current wording.

## Where evidence is thin (treat as design choices, not findings)

- No study was found of LLM interviewers, or of agentic build loops, with *real non-technical users*. The numbers are extrapolated from simulated users, students, professionals or practitioners: 15–25 minutes, one question per turn, vocabulary sizes, "consolidate every ~5 changes".
- The whole stack was measured on one Windows 11 machine with Smart App Control off. Nothing was run on a Mac, with SAC enforcing, under a Group Policy execution policy, behind a TLS-inspecting proxy, or under a real company `requirements.toml`. The Codex desktop app's UI was not tested.
- No 2026 head-to-head benchmark of AI code reliability across stacks was found. Electron won on what the bake-off measured (no admin, no network, HTML UI, tied code quality), not on a reliability advantage. The HTML fallback built from the Electron UI is designed, not built.
- No independent benchmark of the current cheap models on invoice fields was found, and the share of a plan's allowance one invoice uses is unknown. The skill must run the user's own sample (20–30 hand-checked documents for a real rollout).
- `node:sqlite` is a release candidate, ExcelJS has had no release since 2023, and the data-loss tests used one hand-made fixture, not Excel-authored files. The fidelity check is a heuristic.
- The MCP path was tested only against Codex CLI 0.157.1 in a throwaway folder; the full path in a trusted project folder, app behaviour on config changes, and org allow-lists were not.
- Evidence for low fidelity per se is weak. Evidence for multiple alternatives is strong.
