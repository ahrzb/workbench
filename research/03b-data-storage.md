# Data storage defaults for local personal tools (SQLite vs Excel/CSV), Electron + TypeScript

Scope: what an AI agent should choose, and how it should behave, when a small tool built for an office worker (who is not a developer) must keep or touch data. Stack: Electron 44 + TypeScript, no native Node modules ([03a](03a-default-stack-runtime.md)). Registry, docs and repository facts were read live on 2026-09-29. Tags: `[LOCAL]` = tested on this machine (Windows 11 build 26200, standard user, timezone W. Europe) with the official Node 24.21.0 zip (SHA-256 checked against `SHASUMS256.txt`) and Electron 44.4.5 from the local Electron cache. `[INFERENCE]` = my reasoning. `[UNVERIFIED]` = not confirmed from a primary source or a test.

## Recommendations

1. **Ask one question before choosing storage: "Who is the source of truth, and will a person open, edit or email this file?"** Use the decision table below. Rule of thumb: if the *app* creates and updates the records, use SQLite. If the *user* creates and edits the records in Excel, leave them in their file. SQLite's own guidance: it "competes with fopen()", suits application file formats, and is a single file that "can be written to a USB memory stick or emailed" [1][2]. Excel is right when the human is the editor and the recipient is a human [11].

2. **Do not create a database for v1 if the app only reads a spreadsheet and produces a report.** Read the user's file, write a *new* output file, and stop. Introduce SQLite only when the app has data of its own: history, new records, settings, or state that survives between runs. This follows the build-trap principle. It also avoids the "half-migration" trap of two live copies of the same data [49]. That source is a low-quality vendor blog; treat the point as opinion.

3. **App-owned data goes in one SQLite file in a per-user, non-roaming application folder: `%LOCALAPPDATA%\<AppName>\data\` on Windows (shipped: `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\data`, see below), `~/Library/Application Support/<AppName>/data/` on macOS. Not the project folder, not Documents/Desktop, never a synced or shared drive.**
   - *Why not the default Electron folder.* `app.getPath('userData')` defaults to `%APPDATA%` (the Roaming folder) on Windows, and Electron's own docs warn that "some environments may backup this directory to cloud storage" [38]. Microsoft lists Roaming (`%APPDATA%`) and Local (`%LOCALAPPDATA%`) as separate known folders [48]; Roaming User Profiles copy the profile to a file share [46]. So build the path from `process.env.LOCALAPPDATA` (fallback `app.getPath('userData')`), `mkdirSync(..., {recursive: true})`, and use a `data` subfolder so it does not collide with Chromium's own folders [38]. [INFERENCE: I did not find a Microsoft page that says which of the two folders a company's roaming profile includes; the Local one is the safe choice either way.]
   - *Shipped path (starter `dataDir()`).* `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\data`, not `%LOCALAPPDATA%\<AppName>\data`. `TOOL_ID` is a short name plus 6 random letters, fixed in `main.ts` when the starter is copied and never changed, so renaming the tool cannot orphan its data. The environment variable `WORKBENCH_DATA_DIR` overrides the path: "go back" starts an older build against a *copy* of the current data before it replaces the working tool ([06](06-build-loop.md)). Backups of real data go to `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\backups\<yyyy-mm-dd-hhmm>[-label]\` (macOS `~/Library/Application Support/WorkbenchTools/<TOOL_ID>/backups/`), beside `data` and outside the project, so a synced project folder never uploads them. (v0.1.x kept them under `%LOCALAPPDATA%\Workbench\backups\<project folder>\`; since v0.2.0 a project holds several tools, and each tool's backups sit with its own data.) macOS paths are untested.
   - *Why not the project folder.* (a) The project may itself sit in Documents or Desktop, which OneDrive can back up [22]; on macOS iCloud does the same [23]. (b) The project is under save points ([06](06-build-loop.md), [07](07-codex-host.md)): code can go back to an old save point, the database cannot, so the code and the schema drift apart, and real data would either be committed or silently excluded [INFERENCE]. (c) The user's data must survive "update the workbench" and re-setup of the project; a folder the AI owns is at risk, a folder the tool owns is not [INFERENCE]. Give the app an "Open data folder" button and a "Back up now" button (Rec 19) so the data is never invisible.
   - *This machine.* `%LOCALAPPDATA%` is `C:\Users\<name>\AppData\Local`; `%OneDrive%` is `C:\Users\<name>\OneDrive`; the former is not under the latter, and the real path equals the reported path [LOCAL]. No source says these folders are excluded from OneDrive on every PC; Known Folder Move covers Desktop/Documents/Pictures [22] [INFERENCE].
   - *Startup guard (cheap, catches the ruinous case).* Before opening the database, refuse a path that starts with `\\` (UNC share) or lies under `OneDrive`, `OneDriveConsumer` or `OneDriveCommercial` [UNVERIFIED: the last variable name], and fall back to the local folder. Shipped differently: the starter has no such check in `dataDir()`; instead the setup skill refuses a *project* folder under `OneDrive`/`OneDriveCommercial`, a folder named like `Dropbox`, `Google Drive`, `iCloud` or `Box`, or a `\\` path, and asks for a local folder such as `%USERPROFILE%\Workbench\<name>`. SQLite warns that network-filesystem locking is unreliable and that this can corrupt the file [1][3][5]; practitioners report synced folders as a repeat cause [25]. This is the rule in [08](08-security-compliance.md) rec 8 ("never put one database file on a network or synced drive for several people at once"): sharing means each person has their own database, or one person writes and others receive exported files, or it becomes a server (an IT project).

4. **Never write into the user's original spreadsheet.** Copy it to a backup folder (timestamped, with a SHA-256 in the log; shipped location in rec 3), read from the copy, and write results to a *new* file (`Report 2026-09-29.xlsx`). Write to a temp name in the same folder and rename once complete (Rec 17). A round trip through a library can silently drop content, and on this stack neither ExcelJS nor SheetJS warned when it did (Rec 7) [LOCAL][28][26].

5. **Standard pattern once the app needs data of its own: "read Excel → own SQLite → export Excel".** The spreadsheet is *input only*. The app never edits it. The app owns the SQLite records. The export is a fresh, correctly typed xlsx for people. Keep an `import_log` table (file name, hash, timestamp, rows read/inserted/updated/skipped, warnings). Make re-import idempotent using a stable row key or content hash. Tell the user plainly: "Changes you make in the spreadsheet after import don't flow back unless you import again."

6. **If the user insists the app change their existing .xlsx, run an escalation ladder and stop at the first rung that works.**
   (a) Don't: write a new output file (default).
   (b) Write to a separate "app-managed" workbook the app created; people may add sheets but not edit app columns.
   (c) Change single cells with `xlsx-populate` 1.21.0, the one pure-JS library that kept every part in my test (chart, shape, extension validation, picture, conditional formatting, comments) while changing two cells [LOCAL]. Its last release is 2020-03-01 [44], so it is unmaintained-looking; first run the fidelity check from Rec 7 on a copy of the user's real file, on every file, every time.
   (d) Stop and tell the user why. Editing in place with ExcelJS or SheetJS CE is not a rung on this stack: both dropped content silently in the same test (Rec 7).
   Never edit `.xlsm` (macros) in place. [I did not test macro preservation with any Node library: UNVERIFIED.] Driving Excel itself (COM, from a PowerShell child process) would give top fidelity but needs Excel and a scripting host that company policy may restrict; not researched [UNVERIFIED].

7. **Silent loss is the norm, so the app must make its own stop sign: a fidelity check before any in-place write, and a refusal on doubt.** Python's openpyxl at least warns ("Data Validation extension is not supported and will be removed"), and its maintainer says saving after that warning permanently removes the extension [26][27]. The JS libraries do not warn. On a hand-built "Excel-like" fixture (an ExcelJS file to which I added a chart, a drawing shape and an `x14` cross-sheet data validation) [LOCAL, Node 24.21.0 and Electron 44.4.5 gave identical results]:

   | Item after load + save, no edits | ExcelJS 4.4.0 | SheetJS CE 0.20.3 | xlsx-populate 1.21.0 |
   |---|---|---|---|
   | Chart part | lost | lost | kept |
   | Drawing shape | lost | lost | kept |
   | `x14` extension data validation | lost | lost | kept |
   | Ordinary data validation | kept | lost | kept |
   | Conditional formatting | kept | lost | kept |
   | Picture | kept | lost | kept |
   | Comments/notes | kept | kept | kept |
   | Warning or error printed | none | none | none |

   The fixture was made by me, not by Excel: it shows what each library keeps or drops, not whether Excel would open my chart. SheetJS CE also lost bold formatting on a plain file (0 bold fonts after save, 1 before, `cellStyles: true`) [LOCAL]. This agrees with the direction of an independent 2026 practitioner test [28], and with the open ExcelJS request "removes the charts when reading the file" [29].
   **Fidelity check (about 25 lines with `jszip` or `fflate`):** unzip the original and the result; every part name in the original must exist in the result; the counts of `<dataValidation`, `x14:dataValidation`, `<conditionalFormatting`, `<drawing`, `<legacyDrawing`, `<tableParts` and `<extLst` in each sheet must match. Any difference, or any part name containing `chart`, `pivot`, `vbaProject`, `externalLink`, `slicer` or `ctrlProp` in the *input*, means rung (d): report in plain words ("your dropdown lists would be lost") and fall back to Rec 4. Never suppress a library warning either.

8. **Preflight the file before touching it.** (i) Locked: if the file is open, Excel holds a lock and a hidden `~$name.xlsx` owner file exists next to it. An orphaned owner file after a crash causes false "locked" errors [18][19]. Check for the `~$` file, and catch `EBUSY`/`EPERM` from Node. Say: "Please close the spreadsheet in Excel, then tell me." Copy the original to a temp file and read the copy, so the app holds no handle on the original. In my simulation (another process holding the file with `FileShare.Read`, then `FileShare.None`) [LOCAL; a simulation, not Excel itself, and the sharing mode Excel uses was not checked: UNVERIFIED]:

   | Action from Node on Windows | Held with `FileShare.Read` | Held with `FileShare.None` |
   |---|---|---|
   | `readFileSync` / `copyFileSync` | works | `EBUSY` |
   | open for writing | `EBUSY` | `EBUSY` |
   | `renameSync(new → locked target)` | `EPERM` | `EPERM` |
   | `rmSync(locked)` | `EPERM` | `EPERM` |

   So the copy-to-temp read may or may not work while Excel has the file open; both `EBUSY` and `EPERM` map to the same plain message. Renaming a finished temp file over an existing file works when nothing holds the target [LOCAL], which is one more reason always to write a *new* name (Rec 4, 17).
   (ii) Cloud: if the path is in OneDrive/SharePoint/iCloud, tell the user the file is synced. OneDrive Files On-Demand is on by default and "online-only" files download when opened [21]. AutoSave/sync can create conflicted "Copy" files or "Can't Save Your Changes" merge errors [24]. Do not write into synced folders while Excel is open.
   (iii) Format: read the first bytes before parsing. An xlsx is a zip (`PK\x03\x04`). Legacy `.xls` and password-protected xlsx are both old-style OLE files starting `D0 CF 11 E0` [INFERENCE]. SheetJS CE returned no error on a text file renamed to `.xlsx` (it parsed it as text), while ExcelJS and read-excel-file 9.3.10 threw ("is this a zip file?", "Doesn't look like an `.xlsx` file") [LOCAL], so never rely on an error alone. Detect `.xls`, `.xlsm`, encrypted files and more than 1,048,576 rows [20], and stop with a plain explanation ("please save it as .xlsx and tell me").

9. **Validate the sheet's shape against a contract, never by position.** Locate the header row by scanning for expected column names (trim, case-fold), then build a `name → column index` map from it. Refuse with a specific diff if columns are missing, renamed, or duplicated. Detect merged cells, blank spacer rows, totals rows, notes above the header, and multiple tables per sheet. Humans add all of these; the recognised rules for data-friendly spreadsheets are: one header row, one rectangle, one thing per cell, no colour-as-data, no calculations mixed into raw data [11]. Ask the user to confirm the detected layout in their own words before importing ("I see 3 columns: Name, Date, Amount; the first row is the header; 212 rows. Right?"). Sheet-name lookup must tolerate renames: match by name, fall back to position, and warn. ExcelJS gives `row.values` (1-based, index 0 empty) and `getWorksheet(name)`; both were used this way in the round-trip test [LOCAL].

10. **Read cached values; never treat formulas as inputs.** ExcelJS returns a formula cell as `{formula, result}`; use `.result` and ignore the formula [LOCAL]. read-excel-file 9.3.10 returns just the cached value (2469 for `=D2*2`) [LOCAL]. SheetJS CE gives `{t, v, f, w}` where `v` is the cached value [LOCAL]. A file that no spreadsheet program has calculated has no cached value: ExcelJS wrote `<c r="C1"><f>A1+B1</f></c>` with no `<v>` when I gave no `result`, and read it back as `{formula}` with no result [LOCAL]. So when the app writes formulas, always pass `result` too, or viewers that do not calculate show blanks; the workbook had no recalculate-on-open flag (`<calcPr calcId="171027"/>` only) [LOCAL]. Use US-English function names and comma separators in stored formulas [INFERENCE: file-format convention, not re-checked here]. Rule: write formulas only for humans to see; the app must never read them back.

11. **Convert types at the boundary, and make dates explicit.** SQLite has no date type; store ISO-8601 text (`YYYY-MM-DD`) [9]. Excel stores dates as serial numbers, relative to local time, with no timezone, and keeps a 1900 leap-year bug for Lotus compatibility [15]; SheetJS's docs say a JavaScript `Date` is timezone-aware, so the mapping is ambiguous [33]. Measured on the same file (machine timezone UTC+2): ExcelJS and read-excel-file returned `2026-09-29T00:00:00.000Z`; SheetJS CE with `cellDates: true` returned `2026-09-28T22:00:00.000Z` for the same cell [LOCAL]. Rule: always write dates as `new Date(Date.UTC(y, m-1, d))` with a `numFmt` such as `yyyy-mm-dd`; read them with ExcelJS and take `toISOString().slice(0, 10)`; never use `getDate()`/local-time methods; never write locale-formatted date strings. Use `STRICT` tables so the database rejects wrong types instead of coercing them [10]; verified: `cannot store TEXT value in REAL column` [LOCAL].

12. **Store identifiers as text and warn about Excel's auto-conversion.** Zip codes, phone numbers, order numbers, and SKUs like `1E5` or `2310009E13` must be `TEXT` in SQLite and text-formatted cells in xlsx (`numFmt: '@'` in ExcelJS, and always write the value as a JavaScript string). Excel keeps only 15 significant digits [20]. Evidence of auto-conversion damage is large: gene symbols such as SEPT2 became dates ("2-Sep") and identifiers became floats; a 2016 screen of 35,175 supplementary Excel files found errors in 19.6% of papers with gene lists (704 papers) [13]. A 2021 re-scan found 30.9% (3,436 of 11,117) and identified an extra failure mode, five-digit serial numbers [14]. Excel and Google Sheets converted names in all three modes tried (open, paste, type); formatting destination cells as plain text avoided it [14]. Round trip verified: `000123`, `1E5`, `2310009E13` and a 20-digit number written as strings came back as identical strings in ExcelJS, SheetJS CE and read-excel-file [LOCAL]. If the *source* file stores an ID as a number with a display format (123 shown as `00123`), the leading zeros are not in the data: ExcelJS gave `123` and `.text` `"123"`, SheetJS CE gave `v` 123 and `w` `"00123"`; I did not test read-excel-file on this case [LOCAL]. For ID columns read SheetJS's formatted text `w`, or ask the user to confirm the width of the ID, rather than trusting the number.

13. **Prefer xlsx over CSV as the file format handed to the user; write and read CSV with plain code (about 30 lines, no library).** **Read:** decode UTF-8 and strip a BOM if present [17]; detect the delimiter from the first line, because the list separator comes from the Windows regional setting and in decimal-comma locales Excel uses a semicolon [16]; parse quotes (`""` escapes, embedded newlines, `\r\n`), and keep every field as a string. If a CSV is opened with SheetJS instead, pass `raw: true`: by default it turned `000123` into 123 and `1E5` into 100000 [LOCAL]. **Write for Excel:** UTF-8 *with* BOM (Excel opens UTF-8 CSV "normally if it was saved with BOM"; otherwise the user needs a Data > From Text/CSV import) [17], `\r\n` line ends, quote any field containing the delimiter, a quote or a newline. Match the delimiter to the user's locale (ask "do you write 3,5 or 3.5?" rather than "what delimiter?") [16]. Warn that double-clicking a CSV applies "current default data format settings" [16], which strips leading zeros and converts dates. **Security:** neutralise cells beginning with `=`, `+`, `-`, `@` (or tab/CR); OWASP notes Excel-specific caveats and that there is no universal sanitisation [34]. Round trip verified with comma and semicolon files: quotes, a comma inside a field, an embedded newline, umlauts, `1E5`, and a 20-digit ID all came back equal (after the neutralising prefix), the file started `EF BB BF`, and the delimiter was detected correctly [LOCAL].

14. **Write new xlsx with ExcelJS 4.4.0; style it for humans.** Header row bold, frozen (`views: [{state: 'frozen', ySplit: 1}]`), `autoFilter`, sensible column widths, real number/date formats, one table per sheet. Include a `README`/"About" sheet with export date and source. Write to a `.tmp` name and rename (Rec 17). Reopen the file with a reader and compare row counts and the ID column as strings after writing. Verified in Node 24.21.0 and in Electron 44.4.5 [LOCAL]: frozen header, autofilter, column formats, list validation, conditional formatting, a picture, a note and formulas with cached results were written, and the file re-read with ExcelJS and SheetJS CE (read-excel-file read the same file's values and formula results too). The Electron run used Electron 44.4.5 as a plain Node (`ELECTRON_RUN_AS_NODE`), not a window. The Electron bake-off also round-tripped an xlsx through ExcelJS inside the packaged Electron app [47]. **Shipped (v0.2.0):** the `blocks/excel/` block is the reader and writer the AI copies: read by header name (never position), IDs kept as text, typed dates and numbers, csv in any common dialect, load warnings shown as a stop sign; write with typed columns, frozen header and filters; ExcelJS 4.4.0 pinned; 31 tests [LOCAL]. The xlsx is read in the main process, by design, behind size and zip checks.

15. **SQLite default: Node's built-in `node:sqlite`, in the Electron main process only. No package, no native module.**
   - *Available and usable.* Electron 44.4.5 embeds Node 24.21.0 [37]. In a real Electron 44.4.5 main process, `require('node:sqlite')` loaded with no flag and no warning, exports `DatabaseSync, StatementSync, Session, constants, backup`, and reports SQLite 3.53.4. Stock Node 24.21.0 gave the same SQLite version and exports [LOCAL]. Stability: "1.2 – Release candidate" since Node 24.15.0 (it was 1.1, needs no flag since 22.13, and prints an `ExperimentalWarning` on 22.x; Node 22.23.2 on this machine printed it, with SQLite 3.51.3) [36][LOCAL]. Native-module rules do not apply: Electron's docs require native modules to be recompiled against Electron's ABI [39], and `node:sqlite` is part of Node itself.
   - *Why this one.* It is the only option that is (i) no install and no compiler, (ii) file-backed with SQLite's own crash-safe commit, (iii) current SQLite, (iv) maintained together with the runtime the app ships. Compared: `sql.js` and `node-sqlite3-wasm` in the table below.
   - *Main process only.* The renderer is sandboxed with no Node ([03a](03a-default-stack-runtime.md)); the renderer asks the main process through a narrow IPC API and never sees SQL. The API is synchronous (`DatabaseSync`), so it blocks the main process while it runs. Measured [LOCAL]: 100,000 inserts in one transaction 90 ms (94 ms inside Electron as Node); `count(*)`+`sum` over 100,100 rows 4 ms; but 100 separate autocommitted inserts 1.1 s, about 11 ms each (each commit waits for the disk; `synchronous` defaults to 2 = FULL). So: one transaction per user action or import, never one per row. Personal-scale data does not need more; behaviour beyond 100,000 rows was not measured.
   - *Build gotcha (Forge + Vite).* `import { DatabaseSync } from 'node:sqlite'` must keep the `node:` prefix (`sqlite` alone does not exist). Forge's Vite plugin marks as external every name in `require('node:module').builtinModules` plus its `node:` form [40]; on Node 24.21.0 that list contains `node:sqlite` but not `sqlite` [LOCAL]. With those externals, Vite 8.3.1 emitted `require("node:sqlite")`. Without them (a plain Vite library build), it emitted an empty stub `module.exports = {}`, so `DatabaseSync` is undefined at run time and the warning is only "externalized for browser compatibility" [LOCAL]. After building, check that the main bundle contains `require("node:sqlite")`. The externals list comes from the Node that runs the build, so keep build Node and Electron Node on the same line (Node 24, [03a](03a-default-stack-runtime.md) rec 5). **This was a real bug in the shipped starter, found by the `data-safety` block [LOCAL]:** Vite stubbed out `node:sqlite` in the starter's main-process build. The starter's `vite.main.config.mts` now externalises `node:sqlite`, and the block's README has the same one-line config; the block's `copyData` also detects the empty stub and refuses to use it.
   - *Rule for updates.* Electron majors bring a new Node; on each Electron update re-read the stability index and run the migration and backup tests.

16. **`node:sqlite` settings and traps for AI-written code.** One writer connection, opened as `new DatabaseSync(path, { timeout: 5000 })`. Foreign keys are ON by default and `defensive` is ON by default since 24.14; the busy `timeout` defaults to 0, so set it [36][LOCAL]. Tables `STRICT` [10]. Default rollback journal (`journal_mode` = `delete`) [LOCAL] for a single-user desktop tool unless a concurrency need is shown. WAL adds `-wal`/`-shm` sidecar files (all three were there while open; only the main file after close) [LOCAL], cannot work over a network filesystem, and SQLite notes it makes the DB "less appealing for use as an application file-format" [4]. Losing or copying the DB file without its sidecars corrupts it [5]. Always bind parameters. Traps seen in local tests [LOCAL]:
   - There is no `db.pragma()` and no `db.transaction()` (both are `undefined`); use `exec('BEGIN')` … `exec('COMMIT')` with `ROLLBACK` in a `catch`. Older training data assumes the better-sqlite3 API.
   - `StatementSync` has no `close()` method in 24.21.0/Electron 44.4.5, although the 24.21.0 docs example calls `insert.close()` [36]: `TypeError: ins.close is not a function`. Do not call it; statements are released when the database is closed or garbage-collected [INFERENCE: not tested].
   - **A `Date` or plain object passed as the *first* argument to `run()/get()/all()` is read as a named-parameter bag: no error, and the parameter binds as `NULL`** (a `Date` as a later argument throws `ERR_INVALID_ARG_TYPE`). Convert dates to ISO strings before binding; never pass objects.
   - `undefined` throws; booleans store as 1/0; integers above 2^53 throw `ERR_OUT_OF_RANGE` on read unless `readBigInts` is on (another reason IDs are `TEXT`) [LOCAL][36].
   - `PRAGMA user_version = N` takes a literal, not a bound parameter.
   - A second connection could not write while the first held a lock: `database is locked` after the timeout [LOCAL]. One connection, in the main process, is the design.

17. **How files are written safely: three different cases.**
   - *The database file: never write it yourself; SQLite's commit is atomic.* SQLite makes a transaction appear atomic even across "an operating system crash or power failure" in rollback mode [35]. Tested by hard-killing (`SIGKILL`, `TerminateProcess`) a process in the middle of a 300,000-row uncommitted transaction: 19 MB of uncommitted pages and a `-journal` file were on disk; on reopen the database had exactly the 1,000 committed rows, `integrity_check` = `ok`, and the journal was gone [LOCAL]. That is a process kill, not a power cut, and not a synced or network drive. Never delete or move a `-journal` file by hand [5].
   - *Backups.* Use `await backup(db, tmpPath)` from `node:sqlite` (SQLite's online backup API, since v23.8 [36]) or `VACUUM INTO` [5][6]; never copy the live file. Then open the temp file with `{ readOnly: true }`, run `PRAGMA integrity_check`, compare a row count and `user_version`, and only then `renameSync` it to `backup-YYYY-MM-DD-HHmm.db`. `backup()` overwrites an existing target [36]; `VACUUM INTO` refuses one (`output file already exists`) [LOCAL]. The `backup()` copy passed `integrity_check` (`ok`) and held all 1,001 rows and the same `user_version`; the `VACUUM INTO` copy was created (49,152 bytes) but I did not integrity-check it [LOCAL]. Keep the last N (for example 10), and restore one at least once during development [25]. **Shipped (v0.2.0):** this is the `blocks/data-safety/` block (backups taken by `VACUUM INTO`, restore that first keeps a `before-restore` copy, 20 tests, packaged app verified [LOCAL]); the AI copies it instead of writing this code from prose.
   - *Exports and user files.* Write `Name.xlsx.tmp` in the destination folder, reopen and check it, then `renameSync` to a **new, unique** name (timestamp). Do not rely on replacing an existing file: renaming over a file another process holds fails with `EPERM` [LOCAL].

18. **Migrations: a numbered list of idempotent migration steps and `PRAGMA user_version`.** The user-version integer lives in the database header and is left entirely to the application [7]. At startup: read `user_version`, take a backup (Rec 17), run pending steps in one transaction (`BEGIN … COMMIT`; DDL is transactional in SQLite [INFERENCE from [2]]), bump `user_version`. Prefer additive changes (`ADD COLUMN`, new tables), which do not change the meaning of old queries [2][8]. For anything else (change type, add constraint, drop/reorder columns) use the documented 12-step create-new/copy/drop/rename procedure [8]. The AI must never "recreate the schema" on a DB that holds the user's data. Test every migration on a copy of a real database. If the database was written by a newer version of the app (`user_version` higher than the code knows), refuse to open it and say so. **Shipped (v0.2.0), in the `data-safety` block:** the data version lives in `data\version.json` (so it covers files that are not SQLite and travels with every backup), not in `user_version` alone; on older data the block makes a `before-upgrade-v<old>` backup, runs the migrations on a private copy and swaps the copy in only if every step succeeds (a failing migration leaves the real data untouched, tested); newer data is refused with a plain message, exit code 1, and the same text in `start-problem.txt` beside `data`. Migrations already shipped are never edited; the next one is added ([06](06-build-loop.md) rec 7).

19. **Ship an escape hatch: "Export everything to Excel" (one sheet per table), "Back up now" and "Open data folder" buttons.** SQLite's "single-file document" model (copy, email, attach) fits the idea of a document; the database schema is also the documentation of the file [2]. Name the file in the user's vocabulary and give it a plain `.db` name (or an app-specific extension) they can recognise. "Back up now" opens the native Save dialog, so the user chooses where the copy goes and can see whether that is a synced folder (warn if so). The `data-safety` block ships an optional Backups screen (list, back up now, go back to a copy) for this.

20. **Provide history in SQLite, not in Excel.** If the user needs "what changed / undo / who did this", add an append-only `history` (or soft-delete flag) table; SQLite explicitly supports trigger-managed undo/redo stacks in the file [2]. Spreadsheet errors are "silent", "hidden among thousands of rows", and "difficult to audit" [14]. In field audits since 1995, 88% of 113 audited spreadsheets contained errors [12].

### Decision table: SQLite vs xlsx vs CSV

| Question | SQLite file | Excel .xlsx | CSV |
|---|---|---|---|
| Who is the source of truth? | The app | The human | An exchange copy only |
| Who edits records? | The app's UI; humans only via SQL tools | Human, in Excel | Nobody; export/import step |

| Row counts | Up to very large; fine for personal data [1] | ≤1,048,576 rows per sheet [20]; slow well before | Same; no cap in the format |

| History / audit | Add tables/triggers [2] | Weak; errors silent [12][14] | None |
| Data types | Strict types (opt-in) [10]; dates as ISO text [9] | Auto-conversion risk [13][14]; 15 digits [20]; date serials [15] | Untyped text; the reader guesses |

## Key evidence

**Which store fits (Rec. 1–3, 5, 19–20).** SQLite says it "does not compete with client/server databases. SQLite competes with fopen()." Its recommended domains include application file formats, replacing ad-hoc disk files, and data analysis; a database is "a single file that can be written to a USB memory stick or emailed to a colleague" [1]. Its checklist for engine choice ends "Otherwise → choose SQLite!" for device-local storage [1]. The application-file-format whitepaper lists benefits relevant to an AI-built app: no new file-format code, single-file documents, atomic transactions, easy extension by adding tables/columns, concurrent readers, trigger-based undo/redo, and a schema that documents the format [2]. Spreadsheet-side evidence is about *risk*, not fit: Panko's field audits found errors in 88% of 113 audited spreadsheets since 1995 [12]; Broman & Woo give data-entry rules (single header row, one thing per cell, ISO dates, no calculations in raw data, backups, plain text for storage) [11]; Abeysooriya et al. conclude spreadsheet errors "occur silently, … can be hidden amongst thousands of rows, and … are difficult to audit" [14]. Read together: spreadsheets are fine for human editing and viewing, dangerous as the sole system of record.

**Where the data lives (Rec. 3).** Electron: `userData` "by convention" holds user data, defaults to `%APPDATA%\<name>` on Windows, and "some environments may backup this directory to cloud storage"; app files belong in a subfolder to avoid Chromium's own folders [38]. Microsoft's known-folder table lists `%APPDATA%` (Roaming) and `%LOCALAPPDATA%` (Local) as separate folders [48]. Roaming User Profiles "redirect user profiles to a file share" [46]. SQLite: file locking "is buggy in many network filesystem implementations," so corruption can occur; WAL "does not work over a network filesystem"; copying the DB or deleting journals/WAL mid-transaction can corrupt it [1][3][4][5]. Microsoft: Desktop/Documents can be backed up to OneDrive [22], Files On-Demand is on by default [21]; Apple: Desktop and Documents can be stored in iCloud Drive and new files go there automatically [23]. A 2026 practitioner post reports the same pattern for SQLite state files in synced folders and recommends excluding the directory and using `VACUUM INTO` or the backup API [25] (opinion, consistent with [5]).

**Locks (Rec. 8).** Microsoft's locked-file pages explain Excel's owner file `~filename.xlsx` [19] and that non-Microsoft-365 locations such as local folders, network shares, and Dropbox do not support co-authoring, producing "locked" errors [18]. A Microsoft Q&A thread describes "Can't Save Your Changes … couldn't merge your changes" errors on OneDrive-hosted Excel files even for a solo user [24]. My simulated-lock test gave the Node error codes (`EBUSY` for reading or opening a fully locked file; `EPERM` for renaming over or deleting a held file) [LOCAL].

**Library round-trip fidelity (Rec. 4, 6–7, 14).** openpyxl docs (kept as evidence of the class of problem, not as a dependency): it "does currently not read all possible items in an Excel file so shapes will be lost from existing files if they are opened and saved with the same name"; `save()` "will overwrite existing files without warning" [26]. On load it warns that unsupported data-validation/conditional-formatting extensions "will be removed"; the maintainer replies that there is currently no way around this [27]. ExcelJS: an open feature request records that it "removes the charts when reading the file" [29]. One practitioner (2026) compared ExcelJS, SheetJS 0.18.5 and xlsx-populate on a workbook with cross-sheet dropdown validations, drawings and styles, and inspected the XML: ExcelJS duplicated validations (7→14) and lost drawings; SheetJS dropped validations, drawings and most styles; xlsx-populate preserved everything [28]. That is one test by one person. My own test (Rec 7 table) used a different, hand-made fixture with the same three libraries, on current versions, and agrees on direction: ExcelJS lost the chart, the shape and the `x14` validation; SheetJS CE lost everything but comments, column widths and the autofilter (frozen pane included); xlsx-populate kept everything [LOCAL]. It differs on one detail: I saw ExcelJS keep the ordinary validation once, not duplicate it, so the duplication in [28] may depend on the validation type [INFERENCE]. Neither ExcelJS nor SheetJS CE printed a warning [LOCAL]. ExcelJS did not compute a formula result when none was supplied [LOCAL].

**Formulas, dates, IDs (Rec. 10–12).** Excel keeps Lotus 1-2-3's leap-year error for 1900 for compatibility, and fixing it would shift almost all dates by a day [15]. SheetJS: the epoch of an Excel date is local midnight, so a JavaScript `Date` is ambiguous [33]; measured, SheetJS and ExcelJS differ by the timezone offset on the same cell [LOCAL]. SQLite has no date storage class; ISO-8601 TEXT is one of three recommended representations [9]. Ziemann et al. 2016 screened 35,175 supplementary Excel files; 987 files in 704 papers (19.6% of papers with gene lists) contained gene-name errors (SEPT2 → date; `2310009E13` → `2.31E+13`); the problem was first documented in 2004; Google Sheets did not convert on typing/pasting in their test [13]. Abeysooriya et al. 2021: 30.9% (3,436/11,117); Excel and Google Sheets converted in all three input modes and LibreOffice/Gnumeric did not; the fix in Excel was pre-formatting cells as text; HGNC renamed genes (SEPT1→SEPTIN1) to dodge it [14]. Excel numbers have 15-digit precision [20].

**CSV (Rec. 13).** Microsoft: opening a CSV uses "current default data format settings"; forcing the wizard (rename `.csv`→`.txt`) preserves leading zeros; the CSV list separator comes from regional settings and a decimal comma forces a semicolon; the limit is 1,048,576 rows [16]. UTF-8 CSV opens correctly only "if it was saved with BOM"; otherwise use Data > Get Data > From Text/CSV [17]. OWASP: cells starting `=`, `+`, `-`, `@` may run as formulas; the tab-prefix mitigation is Excel-specific and pollutes the data [34].

**SQLite on this stack (Rec. 15–17).** Node 24.21.0's `node:sqlite` docs: `DatabaseSync` is synchronous; options `readOnly`, `timeout` (default 0), `enableForeignKeyConstraints` (default true), `defensive` (default true since 24.14.0); `backup(sourceDb, path)` returns a Promise and overwrites an existing target; "Stability: 1.2 – Release candidate" [36]. Electron 44.4.5 embeds Node 24.21.0 [37]; in the real main process the module loaded and reported SQLite 3.53.4 [LOCAL]. Electron's native-module doc requires rebuilding for its ABI [39]; `node:sqlite` needs none. The Forge Vite plugin externalizes `builtinModules` and their `node:` forms [40]. sql.js's README: an in-memory virtual file that "doesn't persist the changes", exported as a typed array, and a recommendation to use a native binding in Electron or Node [42]. node-sqlite3-wasm implements a VFS over Node's `fs` and names Electron as its use case [41]. The official SQLite WASM project is browser-focused, with persistence through OPFS [43]. SQLite's atomic-commit article: transactions "appear to be atomic even if the transaction is interrupted by an operating system crash or power failure" in rollback mode, with the journal file as the recovery record; deleting or renaming a hot journal defeats it [35]. The corruption guide lists safe live-copy methods (`sqlite3_rsync`, `VACUUM INTO`, backup API) and warns about backing up during a transaction and about moving/deleting hot journals [5]. `VACUUM INTO` needs a non-existent or empty target and creates a consistent snapshot; an interrupted run can leave an incomplete file [6]. `PRAGMA user_version` is a free integer "for applications to use however they want" [7]. `ALTER TABLE` supports rename/add/drop column directly; other changes need the 12-step procedure [8]. STRICT tables (3.37.0, 2021-11-27) enforce declared types [10]. WAL is faster and allows readers alongside a writer but adds sidecar files and needs same-host access [4].

**xlsx libraries (Rec. 14, 21).** The SheetJS docs say the npm registry copy is out of date (0.18.5), that `cdn.sheetjs.com` is "the authoritative source", and recommend vendoring the tarball [31]; the CDN tarball's `package.json` shows Apache-2.0 and no dependencies [32]; the project's tags feed lists v0.20.3 (2024-07-18) as the newest release [32]. ExcelJS is MIT, pure JS, last released 2023-10-19, with its last commit on the default branch on 2024-01-12 and 809 open issues; the repository is not archived [30][44]. `read-excel-file` and `write-excel-file` are both maintained in 2026 with small dependency sets, but their READMEs record breaking API changes across several major versions [44][45].

## Open questions and disagreements

- **WAL or not.** better-sqlite3 and Bun docs recommend WAL for performance; SQLite's own docs list sidecar files and no network-filesystem support as WAL drawbacks, particularly for application file formats [4]. Recommendation 16 favours the default rollback journal at personal scale; a judgment, not measured beyond the 100,000-row test.
- **`node:sqlite` is a release candidate, not stable.** The API can still change in a later Node major. The exposure is bounded: Electron pins Node per major, the app uses a small part of the API, and `node-sqlite3-wasm` reads and writes the same file format (its file passed `integrity_check` in `node:sqlite`) [LOCAL]. Whether `node:sqlite` will reach 2.0 (stable) before Electron 44's end of life (2027-03-02, [03a](03a-default-stack-runtime.md) rec 13) is unknown [UNVERIFIED].
- **`StatementSync.close()`.** The 24.21.0 docs example calls it; the runtime in Node 24.21.0 and Electron 44.4.5 has no such method [LOCAL][36]. I did not find out in which release it appears or whether the docs example was published ahead of the code [UNVERIFIED].
- **Blocking the main process.** Measured only to 100,000 rows. A very large import (for example millions of rows) would freeze the window during the transaction; moving it to a worker thread or utility process was not tried [UNVERIFIED].
- **ExcelJS is stalled.** No release since 2023-10-19 and 809 open issues [44]. It is the default because it reads and writes new files correctly in my tests and the AI knows its API well; if it breaks on a real user file, the fallback reader is `read-excel-file`, then SheetJS CE. There is no maintained, complete, pure-JS library that edits xlsx in place without loss [INFERENCE from the table in Rec 7].
- **The fidelity check is a heuristic.** It catches removed parts and counted elements, not changed formatting or reordered content. It was validated only against one hand-made fixture, not against real Excel-authored files of the user [LOCAL]. Excel-authored files (pivot tables, slicers, Power Query connections, external links, sensitivity labels) were not tested.
- **Macro and pivot preservation** with xlsx-populate or any other Node library was not tested (Rec 6) [UNVERIFIED].
- **Can the app read a file while Excel has it open?** My simulation shows it depends on the sharing mode the other process uses; I did not check which mode Excel uses, nor macOS behaviour [UNVERIFIED]. The copy-to-temp approach may itself fail with `EBUSY`; the plain message is the fallback.
- **Does a script's read trigger OneDrive hydration?** Microsoft says online-only files download when opened [21]; a vendor blog claimed plain filesystem reads from tools may not trigger it (search snippet, not verified) [UNVERIFIED].
- **Where are app-data folders synced?** No source states `%LOCALAPPDATA%` or `~/Library/Application Support` are excluded from OneDrive/iCloud; the recommendation rests on the documented scope (Desktop/Documents) [22][23] and on this machine's paths [LOCAL] [INFERENCE]. Which environment variable names OneDrive for Business sets (`OneDriveCommercial`) was not checked [UNVERIFIED].
- **Project folder vs app-data folder.** Resolved in the shipped skill: [07](07-codex-host.md) rec 11's "its data" means `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\data` (Rec 3), and the backups sit beside it in `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>\backups\`. The update owns a fixed list of paths (`update.md`) and never those folders. Removing a tool completely means deleting its folder `tools/<name>/`, its shortcut, and `%LOCALAPPDATA%\WorkbenchTools\<TOOL_ID>` (data and backups), and the skill asks before deleting any data.
- **Thresholds ("more than three editors", row counts).** Vendor blogs give team-scale thresholds [49]; they do not apply to single-user tools. Only the hard limit (1,048,576 rows) is sourced [20]. Practical "slow" limits for Excel are unmeasured.
- **Excel formula recalculation without Excel** (LibreOffice headless or a JS formula engine) was not researched; it likely needs a separate install [INFERENCE].
- **macOS.** `node:sqlite` and the JS libraries are platform-neutral; the paths and lock behaviour above were tested only on Windows [UNVERIFIED for macOS].

## Conflicts with the guiding principles

- **Local-first / "data never leaves the machine without the user knowing" vs. Known Folder Move and roaming profiles.** On many office PCs, Desktop and Documents are already redirected into OneDrive [22]; on macOS the same may hold for iCloud [23]; Electron's default data folder is the Roaming one [38][46]. Saving app output, backups, or the database into "Documents", or leaving the database in Electron's default folder, may therefore upload it, silently to the user. The skill must build the database path itself (Rec 3), check the path, and tell the user where files go.
- **Smallest-useful-thing vs. the "read Excel → own SQLite → export Excel" pattern.** The pattern adds a database and an importer. Applied at v1, it breaks the build-trap principle (Rec. 2 addresses this by making SQLite conditional on the app having data of its own).
- **"AI picks technology" vs. questions about the user's files.** The skill must ask about their data ("who else edits this file? do you email it?") but not about technology. This is compatible, provided questions use their vocabulary.
- **No-admin requirement: no conflict for the recommended stack.** `node:sqlite`, ExcelJS, and the fallbacks need no compiler or installer; the SheetJS tarball needs access to `cdn.sheetjs.com` at install time (or a vendored copy) [31]. An Excel-driving route (COM) would depend on Excel and on PowerShell being allowed; it is not recommended.
- **"Prefer stable" vs. `node:sqlite` at Stability 1.2.** The alternative that meets the no-native rule (WASM) has its own costs: `sql.js` loses unsaved work on a crash and ships an older SQLite; `node-sqlite3-wasm` is a one-maintainer package. The trade is accepted with the fallback above.
